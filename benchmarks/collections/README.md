# 1000 Tabs и Tags: подготовка SSR, клиент и память

Журналы одного локального эксперимента на 1000 элементах одной коллекции,
сравнение исходной и новой схем Soxa и сопоставимых примитивов соседей.
Это не 1000 независимых корней Tabs с двумя вкладками в каждом и не виртуальный список.

Итог с объяснением изменения механизма — [report.md](report.md). Журналы:
[Vue](vue.md), [React](react.md), [Solid](solid.md), [Svelte](svelte.md),
[Angular](angular.md), [Web Components](webc.md). Оптимизация 19.11.2026 —
[2026-11-19-1000.md](2026-11-19-1000.md), оверлеи `initial` только до
принятия 20.11.2026 — [2026-11-20-initial-overlays.md](2026-11-20-initial-overlays.md).
Исходники стенда —
[tools/bench-collections](../../tools/bench-collections).

Исходники ревизий извлекаются в build-кэш без дополнительных checkout/worktree.
Обе используют одинаковые версии фреймворков и компиляторов из lockfile стенда.
Дополнительный контроль `items` необходим: часть работы уже выполнялась до HTML
в старом API данных. Ускорение относительно декларативного пути не следует
автоматически приписывать всей новой механике или переносить на `items`.

## Данные и критерии

- 1000 уникальных значений `v0`…`v999`, подписи `Item 0`…`Item 999`.
- Tabs: второй активен; 1000 объявлений панелей, содержимое только активной
  панели. У Angular неактивные consumer-owned hosts могут оставаться пустыми.
- Tags: одиночный выбор, выбран второй элемент, удаления и ввода тегов нет.
- Без виртуализации и тяжёлого содержимого панелей; metadata плоские.
- Проверяются число элементов, выбранный второй, панель `Panel 1`, взаимные
  `aria-controls`/`aria-labelledby`, если это Tabs.
- Для Soxa отдельно проверяется одна явная Tab-остановка коллекции. У соседей
  модель roving focus может использовать фокус контейнера; её атрибуты
  сохраняются как наблюдение, а клиентский вход Tab проверяется отдельно.

Неполный или некорректный SSR HTML помечается в таблице и не участвует в
утверждении «быстрее выполнил ту же работу». Значения не исправляются повторным
серверным проходом или ручной регистрацией ради зелёного результата.

## SSR

Продуктовые серверные сборки Vite, нативные серверные API пяти фреймворков,
Angular AOT. Web Components не имеют поддерживаемого серверного рендерера Soxa:
для них измеряется клиент, SSR обозначен N/A.

Клетка — отдельный Node-процесс с `NODE_ENV=production` и `--expose-gc`.
После проверки HTML — 3 прогрева и 9 измерений полного рендера; GC выполняется
вне измеряемого участка. Затем отдельная серия памяти: 3 раунда по 3 запроса,
пауза 1200 мс, обороты очереди и GC. Для Soxa считаются живые core-модели и
bundles через `v8.queryObjects`; сравнивается изменение от прогретой базы,
а не абсолютный ноль — в процессе есть штатные модели конфигурации.

Занятая heap после GC — наблюдаемая удерживаемая память. До GC — не точное число
всех аллокаций. Peak RSS — максимум всего процесса: загрузка модулей, проверка
HTML через JSDOM, прогрев и рендеры включены; это не изолированный пик SSR.
Предупреждение Node об экспериментальном `v8.queryObjects` сохранено в raw
и отделяется от диагностики библиотеки.

## Клиент

Настоящий Chromium, 1440×900, DPR 1, production-сборки, без CPU throttling.
Участник/путь получает отдельный браузер. Прогрев — 3 цикла, затем 7 измерений.
DOM-время заканчивается после штатного flush фреймворка; готовый кадр — после
двух `requestAnimationFrame`. Загрузка JS и сборка в эту метрику не входят.

Время, память и действия разделены. В памяти — ещё 7 циклов после временного
прогона: heap/DOM/слушатели после GC с коллекцией и после удаления; финальная
пауза 1200 мс. Клиентский `Runtime.queryObjects` не используется: перечисление
прототипов существенно вмешивалось в один из контрольных прогонов. Все
клиентские участники используют один протокол `client-v3-isolated-phases`.
Ранние протоколы в итоговые цифры не смешиваются.

Отдельная проверка выбора использует полную синтетическую цепочку pointer/mouse,
`MutationObserver` для выбранного DOM-состояния и два кадра. Это не измерение
доверенного аппаратного ввода. Предел клетки — 180 секунд; незавершённая клетка
сохраняет стадию и частичные данные и не получает выдуманную медиану.

Soxa — oren с поведением и Material icons. Ark — headless с минимальными
правилами размещения; shadcn — сгенерированный Tailwind neutral stylesheet;
MUI — штатное оформление. Число DOM-узлов и возможности компонентов различаются:
сравнение соседей показывает цену этих реализаций, а не универсального победителя.

## Воспроизведение

Из корня репозитория:

```powershell
npm.cmd ci
npm.cmd ci --prefix tools/bench-collections
npm.cmd run build:css --workspace=@soxa-ui/theme-oren
node tools/bench-collections/prepare.mjs --prepare
node tools/bench-collections/shadcn-css.mjs
node tools/bench-collections/build.mjs
node --test tools/bench-collections/quality.test.mjs
node --expose-gc tools/bench-collections/controls.mjs
node tools/bench-collections/run.mjs --n=1000 --run=my-run
node tools/bench-collections/interaction.mjs --run=my-run
node tools/bench-collections/publish.mjs --run=my-run
```

Нужны Node 24+, установленный Chromium Playwright и обе исходные Git-ревизии.

Две свои ревизии вместо `before`/`after` задаёт `--revisions` у `prepare.mjs`
(`WORKTREE` — текущее дерево), имена вариантов те же у `build.mjs` и `run.mjs`.
Сравнение двух вариантов одного запуска — `compare.mjs`, быстрая медиана SSR
для итераций (не замер) — `quick.mjs`:

```powershell
node tools/bench-collections/prepare.mjs --prepare --revisions=main=<sha>,head=WORKTREE
node tools/bench-collections/build.mjs --variant=main,head
node tools/bench-collections/run.mjs --n=1000 --run=my-run --variant=main,head --libs=soxa
node tools/bench-collections/compare.mjs my-run main head
node --expose-gc tools/bench-collections/quick.mjs head angular tabs declarative
```

Экспорт создаёт новый raw-каталог и дописывает журналы. Существующий опубликованный
запуск не перезаписывается; для повторения используется новое имя `--run`.

Повторная загрузка shadcn registry — отдельное действие
`node tools/bench-collections/vendor-shadcn.mjs`: новый upstream snapshot требует
нового замера, а не незаметной замены прежнего участника. Raw и журналы дописываются
новыми датированными запусками; старые результаты не переписываются.
