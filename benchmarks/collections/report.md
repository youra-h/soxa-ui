# Что дала предварительная подготовка коллекции

Замер на 1000 элементах проверяет две разные задачи: может ли сервер сразу отдать
правильную коллекцию и сколько стоит её создание и обычная работа в браузере.
Предварительная подготовка решает первую задачу, но не обещает ускорить каждый путь.
Часть старых путей уже принимала готовые данные, поэтому сравнение только с 1000
декларативных детей завысило бы оценку ускорения.

[Методика и состав участников](README.md), [таблица до/после](comparison-2026-11-18-1000.md),
[manifest и все исходные результаты](raw/2026-11-18-1000/manifest.json).
Журналы: [Vue](vue.md), [React](react.md), [Solid](solid.md), [Svelte](svelte.md),
[Angular](angular.md), [Web Components](webc.md).

## Что изменилось в механизме

Раньше декларативные элементы сообщали о себе при выполнении дочерних компонентов.
Родитель ещё не знал полного состава. Например, первый элемент успевал получить
начальную Tab-остановку, а второй позднее объявлял себя активным. Реактивное обновление
состояния не исправляло уже записанный серверный HTML. В React часть регистрации
вообще приходилась на клиентский жизненный цикл. Поэтому одинаковые объявления
компонентов давали разные серверные результаты в разных адаптерах.

Новый `initial` сообщает родителю состав и metadata до рендера детей. Общая механика
проверяет и фиксирует plain snapshot, создаёт модели коллекции, определяет начальный
выбор и заранее готовит связи вкладок с панелями. Дочерние части связываются с уже
подготовленными позициями. Сервер сразу сериализует окончательное состояние.
Тот же источник используется при первом клиентском рендере; после монтирования
работает обычный движок коллекций. Контракт описан в [руководстве](../../docs/ssr-collections.md).

Это явное объявление данных потребителем. Автоматическое обнаружение произвольных
`Item` внутри пользовательских обёрток не появилось. Старый декларативный API сохранился;
само обновление пакета не превращает его в заранее известную серверу коллекцию.
Механизм подготовки общий, но в проверяемой ревизии подключён к Tabs и Tags.

Отдельная часть изменения защищает время жизни подготовленной сборки React.
Принятая сборка подтверждается, брошенная — откатывается транзакцией движка.
Внешние модели сохраняют своего владельца. Отложенная очистка освобождает ресурсы
непринятой сборки; её срок не означает ожидание секунды перед выдачей HTML.
Обычный Suspense остаётся обычным Suspense. Этот нагрузочный замер использует
завершённые рендеры; ветви отмены и повторов отдельно проверены в
[SSR acceptance](../../tools/ssr-acceptance/INTEGRATION.md).

## Сервер: корректность и цена

`initial` сформировал корректные 1000 элементов, выбранный второй элемент, одну
Tab-остановку и взаимные ID вкладки/панели на всех пяти серверных адаптерах.
Декларативный путь Vue, React, Solid и Svelte сохранил прежние ошибки начального
SSR-состояния. Angular прошёл эти проверки и до изменения. Web Components не имеет
поддерживаемого серверного рендерера Soxa: его SSR — N/A, клиент измеряется полностью.

Сравнение с уже корректным старым `items` показывает цену новой схемы точнее:

| Адаптер | Tabs: до `items`, мс | Tabs: `initial`, мс | Изменение | Tags: до `items`, мс | Tags: `initial`, мс | Изменение |
| ------- | -------------------- | ------------------- | --------- | -------------------- | ------------------- | --------- |
| Vue     | 166.0                | 178.2               | +7.4%     | 144.4                | 143.8               | −0.4%     |
| React   | 82.0                 | 131.3               | +60.2%    | 58.8                 | 73.7                | +25.2%    |
| Solid   | 163.3                | 131.1               | −19.8%    | 98.7                 | 105.1               | +6.4%     |
| Svelte  | 147.7                | 117.6               | −20.3%    | 96.0                 | 88.0                | −8.3%     |
| Angular | 478.0                | 450.2               | −5.8%     | 274.1                | 263.8               | −3.7%     |

Знак плюс означает замедление. Это медианы девяти рендеров на одном компьютере,
а не доверительный интервал и не обещание тех же процентов на другом сервере.
Особенно заметна цена React Tabs: подготовка и управление временной сборкой
не бесплатны. Нельзя представлять этот результат как универсальное ускорение.

Без изменения потребительского кода путь `items` тоже иногда стал медленнее:
Vue Tabs — 166.0 → 212.3 мс (+27.9%), React Tabs — 82.0 → 88.4 мс (+7.9%),
Angular Tabs — 478.0 → 565.5 мс (+18.3%). Другие случаи стали быстрее.
В ревизии изменились общие расширения и жизненный цикл сборки; эти цифры включают
всю разницу ревизий. Они не доказывают, что весь прирост времени вызван одним
клонированием snapshot или одним конкретным обработчиком.

Большой выигрыш относительно декларативных детей объясняется ещё и способом
инициализации. Вместо постепенных регистраций 1000 детей родитель заранее получает
готовый состав. Например, Vue Tabs после изменения: 955.6 мс через детей и 178.2 мс
через `initial`. Но первый результат имеет неверный SSR HTML: это наблюдение
стоимости разных путей, а не доказательство ускорения одной и той же корректной работы.

## Клиент: ускорение зависит от исходного пути

У обычного клиента уже была реактивная регистрация детей. Предварительная подготовка
убирает её постепенность, но добавляет snapshot и связывание частей. Поэтому
сравнение с прежним `items` в большинстве случаев показывает дополнительную цену:

| Адаптер        | Коллекция | До `items`, мс | После `items`, мс | `initial`, мс | `initial` / до `items` |
| -------------- | --------- | -------------- | ----------------- | ------------- | ---------------------- |
| Vue            | Tabs      | 136.7          | 140.8             | 173.2         | +26.7%                 |
| Vue            | Tags      | 95.3           | 108.5             | 111.2         | +16.7%                 |
| React          | Tabs      | 107.2          | 90.9              | 113.4         | +5.8%                  |
| React          | Tags      | 53.3           | 79.5              | 83.7          | +57.0%                 |
| Solid          | Tabs      | 92.1           | 99.6              | 124.9         | +35.6%                 |
| Solid          | Tags      | 66.0           | 80.6              | 94.6          | +43.3%                 |
| Svelte         | Tabs      | 207.5          | 222.2             | 238.2         | +14.8%                 |
| Svelte         | Tags      | 171.1          | 144.8             | 186.4         | +8.9%                  |
| Angular        | Tabs      | 181.9          | 202.8             | 195.3         | +7.4%                  |
| Angular        | Tags      | 93.7           | 77.6              | 117.0         | +24.9%                 |
| Web Components | Tabs      | 216.0          | 268.4             | 282.6         | +30.8%                 |
| Web Components | Tags      | 142.5          | 108.7             | 139.6         | −2.0%                  |

Это DOM-время монтирования, без загрузки JS; время до двух rAF приведено в журналах.
Старые декларативные пути заметно дороже: например, Vue Tabs 515.7 мс против
173.2 мс у нового `initial`, React Tabs 459.4 против 113.4 мс. Этот выигрыш нельзя
приписать только новому коду: прежний `items` уже обходил большую часть цены
постепенной регистрации. Если приложение уже использует `items` и его HTML
корректен, тест не показывает, что переход на `initial` нужен ради скорости.

Небольшие изменения медиан не отделены от вариативности компьютера статистическим
интервалом. Но крупные регрессии, например React Tags, сохраняются в отчёте как
наблюдение, требующее оптимизации, а не скрываются общим средним по адаптерам.

Отдельные CPU-профили серий по пять SSR-рендеров доступны в
[manifest](raw/2026-11-18-1000/manifest.json); `.cpuprofile` можно открыть в DevTools.
У React Tabs `initial` добавляет видимые выборки в `resolveCollectionInitialItem`
и `initialPartProps`; среди крупных общих затрат остаются snapshot чтения связки
и GC. В Vue среди заметных участков — `sourceOf`, proxy-чтения и GC. Это помогает
выбрать места для следующего исследования, но leaf sampling не позволяет разложить
весь прирост времени по одной функции. Профили снимались отдельно и не заменяют
медианы основного прогона.

После инициализации смена выбора работает обычным путём. Все 70 доступных
клиентских сценариев выполнили семь изменений, а все проверенные Tabs пропустили
Tab во вторую выбранную вкладку. Например, Vue Tabs: DOM выбора 14.8 → 14.5 мс
(`items` до → `initial`), React Tabs: 20.6 → 19.3 мс. У Vue Tags DOM-состояние
обновилось заметно раньше: 17.1 → 1.3 мс; время до двух rAF всё равно около
32 мс. Для такого результата нельзя подменять «раньше изменился атрибут»
утверждением о столь же кратном ускорении видимого кадра.

## Как читать память

В SSR сравниваются модели и bundles с прогретой базой, а не с абсолютным нулём:
глобальная конфигурация библиотеки сама содержит модели. После серии запросов,
ожидания очистки и GC во всех завершённых Soxa-сценариях прирост этих объектов —
0 моделей и 0 bundles. Это положительный результат данного теста, но не доказательство
отсутствия любых утечек при произвольном Suspense и внешнем владении.

В raw также сохранены heap до/после GC и Peak RSS. Отрицательный остаток heap после
серии не считается «выигрышем памяти»: освобождаются временные данные прогрева,
инспекции и движка. Peak RSS включает загрузку модулей и JSDOM-проверку HTML,
поэтому его нельзя выдавать за чистый пик одного SSR-запроса. Проверка чувствительности
измерителя отдельно удержала 9 моделей (95 → 104 → 95) и DOM-узлы (13 → 59 → 13).

В клиенте отдельно измеряются живая heap смонтированной коллекции и остаток
после семи дополнительных mount/unmount. Узлы и listeners помогают отличить
удержанное дерево от небольших изменений кэшей JS. Ряды каждого цикла сохранены;
одна разность heap не получает автоматический ярлык «утечка».

В смонтированном состоянии `initial` занимает больше памяти. Относительно прежнего
`items` у Tabs добавилось примерно 2.5–3.1 MiB, у Tags — 1.4–2.0 MiB на 1000
элементов. Это согласуется с наличием зафиксированного источника и дополнительных
связей позиций, но не является разбором аллокаций по классам.
Например, Vue Tabs: 35.98 → 39.04 MiB сверх прогретой базы; React Tabs:
30.73 → 33.78 MiB; React Tags: 20.61 → 22.60 MiB.
После удаления коллекции во всех 70 завершённых клиентских сценариях прирост
DOM-узлов и listeners — 0/0; остаток JS heap меньше 250 KiB. Небольшие остатки
и их траектории опубликованы без заявления об отсутствии любых возможных утечек.

## Найденный предел Solid

Повторное создание и уничтожение декларативных Tabs на 1000 вкладок не завершило
полную клиентскую серию за 180 секунд — и до изменения, и после него. Первые
создания сформировали правильное состояние, затем серия остановилась при
mount/unmount на стадии измерения времени. Прогон не дошёл до измерения памяти,
поэтому по нему нет заключения об утечке и нет итоговой медианы.

Это воспроизведено в протоколе без GC, перечисления прототипов и действий между
временными отсчётами. Первоначальное предположение, что достаточно убрать
вмешательство инспектора, проблему не объяснило. Точная причина внутри механизма
обновления/уничтожения требует отдельного профиля. Данные не позволяют объявить
виноватым сам Solid или новую подготовку коллекции. Пути `items` и `initial` в
Solid завершились; декларативные Tags также завершились. В продуктовый код ради
бенчмарка исправления не вносились.

## Соседние библиотеки

Ark UI проверяется на React, Vue, Solid и Svelte; shadcn/ui и MUI — на React.
У них используются официальные компоненты, а неподдерживаемые сочетания не
подменяются community-портами. shadcn зафиксирован исходниками registry new-york-v4
на Radix, с лицензией, URL и хешами; это не измерение его варианта Base UI.

Tabs сопоставим по задаче: 1000 вкладок, выбранная вторая, содержимое активной
панели. Tags здесь означает одиночный выбор среди 1000 подписей: у Ark это Listbox,
у shadcn — ToggleGroup, у MUI — Chip и небольшой application-owned слой выбора.
Композиция MUI не получает полный клавиатурный контракт Soxa Tags по факту включения
в таблицу. Поэтому цифры показывают стоимость конкретных реализаций, а не скорость
взаимозаменяемых библиотек с одинаковым набором возможностей.

Различаются также DOM, стили и панели. У Soxa подключена oren с поведением и иконками;
у Ark минимальное оформление headless-компонентов; у shadcn скомпилирован Tailwind;
у MUI штатные стили. MUI создаёт одну application-owned активную панель; у других
объявлены 1000 компонентов панелей, неактивное содержимое не монтируется.
Эти различия сохранены в исходниках стенда и не скрываются общим рейтингом.

Для React, где доступны все четыре участника, результат выглядит так:

| Участник             | Коллекция | SSR мс | Клиент DOM мс | Heap коллекции MiB | DOM смены выбора мс |
| -------------------- | --------- | ------ | ------------- | ------------------ | ------------------- |
| Soxa `initial`       | Tabs      | 131.3  | 113.4         | 33.8               | 19.3                |
| Ark UI               | Tabs      | 18.7   | 18.5          | 15.1               | 25.2                |
| shadcn/ui            | Tabs      | 23.0   | 54.3          | 10.6               | 19.3                |
| MUI                  | Tabs      | 24.7   | 75.0          | 21.8               | 62.8                |
| Soxa `initial`       | Tags      | 73.7   | 83.7          | 22.6               | 17.5                |
| Ark UI Listbox       | Tags      | 10.8   | 9.1           | 2.5                | 17.6                |
| shadcn ToggleGroup   | Tags      | 20.5   | 17.3          | 6.8                | 21.4                |
| MUI Chip composition | Tags      | 31.1   | 35.2          | 14.2               | 45.3                |

Все эти строки прошли проверку начального состояния и смены выбора. По созданию
коллекции и живой heap Soxa здесь дороже соседей. Ark UI также быстрее `initial`
в этих сценариях Vue, Solid и Svelte — детали приведены в журналах. При смене
выбора соотношение другое: например, React Tabs Soxa и shadcn имеют близкое
DOM-время, а у MUI оно выше. Из этого нельзя вывести единый порядок библиотек
для всего приложения: измерены конкретные композиции и разные фазы работы.

## Границы результата

Это обычное монтирование клиента и завершённый SSR, без сетевой загрузки JS,
гидратации, виртуализации и конкурентной нагрузки HTTP. Смена выбора измеряется
отдельно от mount и памяти. Ни GC, ни инспекция прототипов, ни действия не добавляются
в серию клиентского времени. Ранние пробные протоколы не смешаны с итоговым
`client-v3-isolated-phases`.

Новая схема даёт детерминированное начальное состояние до сериализации HTML и
управляемое освобождение временных сборок. Цена зависит от адаптера и старого
источника данных. Дальнейшая оптимизация должна сохранять эти свойства и отдельно
измерять цену общего пути `items`, а не опираться на сравнение только с поздней
регистрацией декларативных детей.
