# Upgrading to 0.5.0

These instructions cover the transition from component packages 0.4.2 and themes
0.4.1 to components and themes 0.5.0, with compatible icon packs 0.3.2. Install
these versions after the release workflow has published them to npm.

## Who is affected

| Usage                                                                              | Action                                                                                              |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Standard components, including Tabs and Tags with the supported SSR initial source | Keep the component recipe. No prop, event or slot rename is required by the prepared-state changes. |
| Custom components or plugins reading prepared ARIA/name snapshots                  | Move those reads to mount patches before acceptance and to the model afterwards.                    |
| Custom collection transaction/preparation integration                              | Update transaction calls and ownership; several exported types and methods changed.                 |
| A custom item-group part implemented as a plain object                             | Supply its visible property.                                                                        |
| A custom theme that reads spacing variables or CodeBlock radius defaults directly  | Add the appropriate fallback or read the component's computed CSS property.                         |
| Local CSS setting an existing variable to an explicit length                       | The override continues to win, including zero.                                                      |
| Manual Select/ListBox group separators                                             | Use the new Separator parts when desired; existing applications need no replacement.                |

Keep directly installed core, plugins, setup and adapter packages on the same release.
Update themes with the component minor when their peer range requires it. Icon packs
may receive a compatibility-only patch: their version need not match the library.

## Before

### Prepared mount state

Custom integrations could read getSnapshot()/subscribe() from TNamesPlugin and its
subclasses, TTabsItemIdsPlugin and TTabsContentBindingExtension. They could read
TTabsItemIdsPlugin.initial or TCollectionInitialPartPlugin.aria, and construct:

```ts
const view = new TCollectionAriaState({ state, link, outputs })
const options = collectionInitialOwnerOptions(descriptor, adapterOptions, source)
```

ICollectionAriaLink and ICollectionAriaStateOptions described that old composition.
IPluginMountOptions exposed pluginMount through per-plugin installation options.
A direct TPluginMount.defer() call returned a release function.

### Collection preparation and transactions

```ts
preparation.accept(owner)
const attempt = preparation.prepare(item, {
  owner,
  timeout: 1000,
  initialize() {
    initializeItem(item)
  },
  rollback() {
    releaseAttempt()
  },
})
preparation.release(owner)

// Equivalent low-level driver transaction surface:
const pending = transactions.begin(item, { owner, timeout: 1000, rollback })
transactions.rollbackOwner(owner)
```

IPreparationOptions and generic ICollectionTransactions<Item> exposed item and
owner bookkeeping.

### Theme variable reads

```css
.custom-field-icon {
  gap: var(--so-input-slot-spacing);
  border-radius: var(--so-code-block-radius);
}
```

Those reads assumed that each variable held a ready-made root default.

## After

### Prepared mount state

Prefer the existing collectionInitialState(context, state) helper. It returns a
patched view only while needed and the ordinary state once the mount is accepted.

```ts
const view = collectionInitialState(context, state)
const options = collectionInitialOwnerOptions(adapterOptions, source)
```

If constructing the view directly, use new TCollectionAriaState(state, mount).
Its subscribe(listener) remains available; the new optional acceptance callback
allows a custom state consumer to switch back to the model.

Before acceptance, use TPluginMount.patches, keyed by model field (for example,
mount.patches.aria or mount.patches.closeAria). Plugins can add a patch with
mount.patch(field, values). After mount.accept(), patches are cleared and the
ordinary item model provides aria and closeAria.

Use mount.accepted for the gate's acceptance state. Pass pluginMount through the
adapter context / plugin context; replace imports of removed IPluginMountOptions
with IPluginContext or IAdapterContextOptions as appropriate to the integration.
Do not retain the removed snapshot methods or TCollectionInitialPartPlugin.aria.

TPluginMount.defer(effect) now returns void. Keep teardown with the lifecycle
owner rather than using its return value as a disposer. In a custom TBasePlugin
subclass, the protected _whenAccepted(effect) helper still tracks a returned cleanup.

### Collection preparation and transactions

Initialize the attempt through its existing lifecycle before opening the transaction,
and retain the transaction itself as the acceptance/rollback handle:

```ts
initializeItem(item)
const attempt = preparation.prepare({
  timeout: 1000,
  rollback() {
    releaseAttempt()
  },
})
// The lifecycle owner calls exactly the appropriate terminal operation:
attempt.commit() // accepted
// or attempt.rollback() when abandoned
// or attempt.cancel() when the owner is already releasing the resources

const pending = transactions.begin({ timeout: 1000, rollback })
```

Use ICollectionTransactionOptions instead of removed IPreparationOptions.
ICollectionTransactions no longer has a type parameter; item and owner are no
longer transaction option fields. Remove calls to preparation.accept(),
preparation.release() and transactions.rollbackOwner(); the owner holds the returned
attempt and confirms or rolls it back directly.

ICollectionStorageDriver now exposes readonly revision, matching the built-in driver.
A custom driver must advance it when collection membership/order changes. Direct
driver access remains the collection extension's responsibility.

A custom value satisfying TItemGroupPart must include visible: boolean; the item
group extension uses it to hide groups with no shown members.

### Theme variable reads

For an independently styled normal input field, supply the matching fallback:

```css
.custom-field-icon {
  gap: var(
    --so-input-slot-spacing,
    calc(
      var(--so-spacing, 0.25rem) * var(--so-input-spacing-scale, var(--so-field-scale-normal, 1))
    )
  );
  border-radius: var(--so-code-block-radius, calc(var(--so-radius, 0px) * 4 / 3));
}
```

Choose the matching component family and size for other controls; alternatively,
read the relevant computed CSS property from the rendered component. Explicit
length overrides keep their precedence.

Shared --so-spacing and --so-radius settings now drive defaults, with purpose-specific
size scales. Alert follows the compact Toasts reference at normal size: 0.875rem
block padding, 1rem inline padding and 0.125rem between title and description.
See the [base theme settings and full variable registry](../../packages/themes/base/README.md#shared-radius-and-spacing-settings)
for scales and per-component overrides.

### Compatible additions

Select.Separator and ListBox.Separator provide manual separators between markup
groups. The groupSeparators option retains its data-section behavior; its updated
description explains the distinction. Type declarations also expose the new parts
inside composed controls such as Calendar and DatePicker. No existing consumer
name is removed by those additions.

Adapter assembly helpers reached through declarations are implementation dependencies,
not extra supported entry points. Removing their internal useCollectionInitial or
initialAssemblyProps functions does not change the supported root adapter exports.
Continue using the documented initial source recipe.

## Verification

1. After publication, install the chosen adapter and directly used core/setup/plugins
   at the same component version, together with compatible themes and icon packs.
   Confirm that the exact release versions are available in npm before installing.
2. Run the application's type check, tests and production build. Check the lockfile
   for duplicate Soxa runtimes or peers from an incompatible component line.
3. For SSR collections, retain initial and verify the first HTML, hydration, tab-panel
   ID links and selection with the application's actual recipe.
4. For custom integrations, exercise accepted and abandoned mounts, subscription
   cleanup, group visibility, transaction commit/rollback and any custom driver revision.
5. For custom CSS, check explicit zero/length overrides and fallback defaults across
   the sizes and schemes the application uses.

The compatibility guard compares exact published declarations, component metadata
and documented theme contracts. It does not prove arbitrary runtime, accessibility
or visual compatibility; the existing adapter, theme and consumer tests remain required.
