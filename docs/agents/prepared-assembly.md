# Подготовка сборки компонента

Подготовка объявленного состава `initial` выполняется в общем цикле сборки,
до создания моделей и плагинов. Setup компонентов содержит обычную проводку,
а lifecycle непринятых React-сборок обслуживает механизм транзакций коллекции.
Потребительские примеры — [SSR collections](../ssr-collections.md).

## Порядок

`createAdapterContext` принимает необязательную стратегию через
`config.preparation`. Её `prepare` выполняется до выбора `ctrl`, конструктора
модели, установки плагинов и начальной записи свойств. Результат содержит
опции сборки и необязательное завершение `complete`, которому передаётся
построенный контекст. Завершение не вызывает `attach`.

Защищённая сборка знает только этот протокол. Она не импортирует коллекции
из `content`, не выбирает режим по имени компонента и не вызывает API
фреймворков.

## Коллекции

`TCollectionPreparation` реализует протокол для подготовленного состава.
Подключение объявлено существующими плагинами дескрипторов:

- `CollectionInitialPluginDescriptor` — владелец; у Tabs опция
  `panelDefaultValue: ''` задаёт прежнее умолчание поиска панели;
- `CollectionInitialPartPluginDescriptor` — элемент;
- тот же дескриптор с `panel: true` — панель.

Компонент и фасад сохраняют отдельные контексты. Стратегия выбирает готовую
модель части до её создания и передаёт фасаду обработанные входы через общий
bundle. Владелец связывает подготовленный источник со своим bundle;
`TCollectionExtension` материализует его и опускает через лифт. Чужая или
неподготовленная коллекция закрывает источник предка.

Связку стратегии в конфиг сборки делает `collectionPreparationConfig`:
непричастный компонент получает свой конфиг тем же объектом.

## Принятие сборки и данные монтирования

У подготовленной сборки один признак принятия на весь набор — `TPluginMount`
в опции сборки `pluginMount`. Его получает `TPluginBundle` и отдаёт каждому
плагину в контексте установки (`IPluginContext.pluginMount`). Плагин с ним
откладывает подписки на чужие шины до принятия: `_listenTo` и
`_whenAccepted` ставят вызов в очередь признака, а принятый признак очередь
отпускает, и дальше подписка идёт прямым путём. Принятая сборка держит то же,
что обычная. Обычная сборка признака не имеет и подписывается сразу.

До принятия подготовленная сборка и в общую модель не пишет: движок бывает
общим для запросов сервера, а рендер React — отброшенным. Ссылки таба и
панели (`TTabsItemIdsPlugin`, `TTabsContentBindingExtension`) и имена кнопок
(`_setName` у `TNamesPlugin`) уходят в заплатки признака — `TPluginMount.patch`.
Подписки на чужие шины ждут принятия, поэтому заплатки складываются при сборке
и до принятия не меняются. Читает их только состояние до принятия —
`collectionInitialState` (`TCollectionAriaState`, модель с заплатками поверх):
серверный снимок и рендер React до commit. Принятие сбрасывает заплатки, и те
же плагины пишут значения в модель, как обычная сборка, — те же `id`, что ушли
в серверную разметку. Vue, Solid, Svelte, Angular и Web Components принимают
сборку до первой отрисовки и на клиенте читают состояние обмена напрямую.
React переключает `TStableSnapshot` на состояние обмена при подписке после
принятия. Сравнение снимков по содержимому сохраняет их идентичность, если
значения при этом совпали.
Сторожат `plugins/__tests__/mount.plugin.spec.ts`,
`plugins/__tests__/initial-ids.plugin.spec.ts` и
`setup/__tests__/collection-aria-state.spec.ts`.

`pluginOptions` у подготовленной части — только её собственные: объявление
части (`TCollectionInitialPartPlugin`) и ссылки таба (`TTabsItemIdsPlugin`).

Повторная сборка не должна повторять начальную активацию. Для React и Web
Components `TCollectionPreparationLifetime` сохраняется на срок жизни
нативного монтирования. React создаёт отдельную стратегию на каждый проход
сборки, сохраняя источник по месту вызова владельца внутри той же фабрики.
Web Components сохраняет источник за host при переподключении. Отсутствие
исходного `initial` тоже запоминается: поздний вход не меняет режим монтирования.

## Адаптеры и режимы

Фабрика каждого адаптера подключает одну общую стратегию для участвующих
дескрипторов. Vue дополнительно различает явно переданные свойства и
сгенерированные булевы умолчания; это нормализация адаптера, а не работа
setup каждого компонента. Runtime по-прежнему отвечает за серверный снимок,
клиентскую подписку и момент `attach`.

Подготовленный источник нужен и серверу, и первому клиентскому монтированию.
Флаг SSR не должен превращать один потребительский источник в две разные
модели. Без подготовленного источника сохраняется обычная сборка. Входная подготовка
не требует ожиданий Promise, обхода VNode или обязательного Suspense.
Непричастные компоненты и обычные фасады не подключают стратегию коллекций.

## Непринятые сборки React

После создания всех контекстов React вызывает `TCollectionPreparation.pending`.
Только подготовленная коллекция получает receipt через `TPreparationExtension`
— единственный путь расширения к реестру транзакций, который лениво
принадлежит её driver. Одна запись отвечает за всю нативную сборку, включая
фасады; идентичность попытки — сама запись.

При принятии сборки React делает commit и отпускает квитанцию и ключи
черновика. Если принятия нет в течение 1000 мс,
rollback вызывает идемпотентное уничтожение всей сборки и освобождает запись
`TDrafts`. Исходные модели остаются в engine. Поздний render или установка
эффекта восстанавливает уничтоженную сборку с тем же источником подготовки.
Это ограничение срока владения ресурсами, а не ожидание завершения SSR или
сбора детей.

Очередь таймеров держит только WeakRef реестра: если запрос вместе со своим
движком уже недоступен, его сборка мусора не ждёт timeout. Живой внешний
движок сохраняет реестр до commit или rollback. Setup каждого компонента и
остальные адаптеры не создают транзакций автоматически.

## Границы механизма

Это переработка сборки уже объявленных данных из PR #882. Она не обнаруживает
необъявленные Item в пользовательских обёртках и не превращает декларативное
`Tabs.Item active` в заранее известный состав. Старые вызовы resolver остаются
совместимыми экспортами, но setup компонентов их больше не вызывает.

Регрессии: `packages/setup/__tests__/assembly-preparation.spec.ts` и прежние
`collection-initial` проверки адаптеров. Проверяются момент подготовки,
идентичность моделей, отсутствие повторной инициализации и неизменность
обычной сборки.
