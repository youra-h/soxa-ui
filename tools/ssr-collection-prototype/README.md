# Прототип предварительной сборки SSR-коллекции

Исследовательский результат для [1an4hvw5ykt](https://app.clickup.com/t/1an4hvw5ykt).
Это отдельная инструментированная фикстура, а не исправление адаптера или новый
consumer API. Библиотечные пакеты и защищённый слой не изменяются.

## Запуск

Из корня репозитория:

    npm run check:ssr-collection-prototype

Команда создаёт временную папку, устанавливает закреплённые опубликованные
пакеты npm, запускает серверные проверки и отдельный процесс проверки гидратации.
Путь к папке и report.json печатается в конце. Репозиторий и его node_modules
этот запуск не меняет. Нужен доступ к npm registry.

React 19.3.1, Vue 3.5.44, Svelte 5.57.2, Solid 1.9.17, Angular 22.2.3,
Soxa core/adapters 0.4.0, jsdom 30.1.3. Полный набор закреплён в run.mjs.
Результат запуска сохранён в [results/2026-11-15.json](results/2026-11-15.json).
Исходная ветка перед исследованием: 42fd3e3f1.

## Дополнение: отдельная проверка Vue, Svelte и Solid

Первый этап ниже проверял React и Vue. Его отрицательные React-сценарии
не доказывали необходимость общего механизма для остальных адаптеров.
Дополнение проверяет их независимо; Angular служит контролем без прототипа.
Результат — [results/2026-11-15-cross.json](results/2026-11-15-cross.json).

| Проверка                                                 | Vue                                     | Svelte            | Solid             | Angular без изменений                  |
| -------------------------------------------------------- | --------------------------------------- | ----------------- | ----------------- | -------------------------------------- |
| Разметка, вторая вкладка активна                         | Кандидат: одна остановка вместо двух    | То же             | То же             | Уже одна                               |
| Условие исключает вторую вкладку, активна альтернативная | Одна остановка и панель                 | То же             | То же             | Уже правильно                          |
| Вложенный набор внутри активной панели                   | Одна остановка на набор                 | То же             | То же             | Уже правильно                          |
| Гидратация этих трёх сценариев                           | Узлы сохраняются, переключение работает | То же             | То же             | То же                                  |
| Вложенные наборы в активной и неактивной панелях         | Кандидат отклонён                       | Кандидат отклонён | Кандидат отклонён | Дополнительный механизм не применяется |

В этом кандидате идентификаторы наборов — порядковые номера внутри запроса,
а не useId. Это проверяемая альтернатива, не предлагаемый публичный API.
Простая активная вложенность проходит у всех трёх адаптеров: прежний React-сбой
позиций дерева нельзя обобщать на них. Но scan выполняет содержимое всех панелей,
включая неактивные, а окончательный рендер — только активной. В отрицательном
примере scan регистрирует три набора, final доходит до второго: порядковый номер
видимого вложенного набора указывает на декларации скрытого. Проверка ожидает
конкретную ошибку `Declaration missing`, а не выдаёт её за успешное исправление.
Vue-диагностика этого ожидаемого отказа сохранена в отчёте; положительные сценарии
и гидратация требуют отсутствия console.warn/error без фильтрации.

Гидратация использует отдельно собранные клиентские Svelte/Solid-модули, Vue
createSSRApp и Angular bootstrapApplication с provideClientHydration.
Проверяются сохранение узлов; для трёх кандидатов также id, остановки и независимое
переключение вложенного набора. Среда — jsdom с заглушкой ResizeObserver:
раскладка, реальный Tab и полные Nuxt/SvelteKit/SolidStart-приложения не проверены.
Условие здесь синхронное; async/streaming, смена состава после гидратации,
внешние engine/ctrl и cleanup остаются критериями production-решения.

Измерения дополнения: 100 вкладок, три прогрева, девять измеряемых раундов,
чередование порядка, принудительный GC перед измерением. Discovery также замеряется
отдельно. Сравнивать стоимость discovery следует между prepared и
prototype с одинаковым завершённым HTML. Медианы и все выборки сохранены в JSON.
Разница с baseline включает также другой путь сборки через подготовленный engine;
она не доказывает, что второй проход бесплатный или ускоряет библиотеку.

**Решение:** синхронная возможность исправления подтверждена у каждого адаптера.
Наивный сборщик не готов к внедрению. Необходимость одного общего механизма для
всех не доказана: задачу одной Tab-остановки освободили от обязательного ожидания
общей проработки и связали с ней как related. Выбор решения и регрессии выполняются
отдельно для каждого адаптера. React продолжает собственную ветку исследования.

## Что делает кандидат

Первый серверный проход выполняет инструментированные Root/Item-компоненты и
запоминает декларации в плане своего запроса. Живого engine ещё нет.
Второй проход создаёт engine из полного плана и отдаёт обычным компонентам
Soxa соответствующие ctrl. Активность во время окончательного рендера ведёт
обычный engine; отдельного активного состояния не заводится.

Состав намеренно собирается во время настоящего выполнения компонентов,
а не обходом React children. Проверяется, достаточно ли такого подхода.
Итог: **как общий механизм этот кандидат отвергнут**.

## Что подтвердилось

| Сценарий                                      | Опубликованная библиотека         | Кандидат                                                                                |
| --------------------------------------------- | --------------------------------- | --------------------------------------------------------------------------------------- |
| React, активная вторая вкладка из разметки    | Активной панели нет               | Панель есть, Tab-остановка одна, автоматическая ARIA-связь правильная                   |
| Vue, активная вторая вкладка из разметки      | Две остановки Tab                 | Одна остановка, панель и автоматическая ARIA-связь сохранены                            |
| Собственный id панели, React и Vue            | Связь таба с панелью неправильная | Один сбор вкладок эту проблему не решает                                                |
| React, гидратация простого синхронного набора | Не измеряется этим сравнением     | Узлы таба и панели те же; переключение работает; console/recoverable errors отсутствуют |

У React синхронные элементы дополнительно проходят через пользовательскую
компонентную обёртку. Для Vue проверяется обычная декларативная разметка.

## Почему нельзя переносить прототип в библиотеку

Проверки воспроизводят отрицательные результаты, а не скрывают их:

1. Ветка React Suspense успевает объявить активную вкладку, затем приостанавливается
   и заменяется fallback. План содержит 0, 1 и fallback, но HTML — только Tab 0
   и Fallback. Призрачная вкладка 1 активирует панель, у которой нет таба;
   обе реальные вкладки получают tabindex=-1.
2. При потоковом SSR отрисованный fallback тоже попадает в план. После разрешения
   границы и onAllReady в окончательном HTML его нет, но engine всё ещё содержит
   fallback. Просто дождаться окончания потока недостаточно.
3. Идентичность вложенных наборов, взятая из useId, меняется при замене
   discovery-обёрток настоящим деревом адаптера. Кандидат явно отказывается
   продолжать, а не привязывает набор к чужим декларациям.
4. Сбор вкладок не подготавливает пользовательские id панелей до сериализации
   более ранней кнопки. Начальный контракт должен учитывать связанные части.
5. Переданный снаружи engine кандидат отклоняет без изменения его состава.
   Поддержка внешнего состояния не реализована и не заявлена.

У трёх параллельных запросов планы различны. Это проверяет изоляцию плана,
но не устраняет проблему отменённых веток внутри одного запроса.

Проверка гидратации идёт в отдельном процессе: legacy SSR, streaming SSR и
браузерный React не подменяют друг другу renderer одного Context.
Предупреждения не фильтруются: любой console.warn/error роняет проверку.
Отрицательные сценарии имеют отдельные явные assertions и раздел rejections.

## Измерения

100 вкладок, 5 прогревочных и 9 измеряемых раундов на режим; порядок режимов
чередуется. В JSON находятся среда, все временные выборки и медианы.

- baseline: опубликованная декларативная реализация;
- prepared: окончательный рендер уже подготовленного плана;
- prototype: обнаружение деклараций и такой же окончательный рендер.

Для оценки дополнительного прохода сравниваются prototype и prepared:
результирующий HTML у них соответствует одному и тому же полному набору.
React baseline панели не рисует и не является равной по результату работой.

heap delta снимается сразу после вызова, после принудительного GC перед ним.
Это временные выделения с возможным GC во время вызова, а не peak RSS,
не retained memory и не доказательство отсутствия утечек. Локальные числа
не являются производственным benchmark или обещанием стоимости будущего механизма.

## Границы проверки

Первый этап — React и Vue; дополнение — отдельные кандидаты Vue/Svelte/Solid
и Angular как контроль, которому дополнительная подготовка не требуется.
Гидратация — jsdom, без полных SSR-приложений и браузерного benchmark.
StrictMode/Activity, произвольная асинхронная композиция, повторные изменения
состава и внешние ctrl/engine остаются критериями будущего общего механизма.
Публичное API не менялось; changeset для tools/ не нужен. Merge/release не входят.
