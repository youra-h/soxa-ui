# React: ранний attach и черновики коллекции

Небольшой исследовательский стенд по предложению владельца от 16.11.2026.
Он проверяет альтернативу PR #881/#882 на текущих исходниках main, без initial,
двойного рендера приложения или изменения продуктовых файлов.

## Запуск

Из корня этой рабочей папки с установленными зависимостями:

```sh
node tools/react-early-attach/run.mjs
```

Один режим: установить `ATTACH_MODE=baseline|early|engine|engine-part` и выполнить
`node node_modules/vitest/vitest.mjs run --config tools/react-early-attach/vitest.config.ts`.
Команда `run.mjs` выставляет переменную сама и запускает каждый режим в отдельном
процессе. Новые пакеты и сборка библиотеки не нужны: Vitest использует source aliases.

## Что меняет эксперимент

[Конфиг](./vitest.config.ts) инструментирует настоящий React runtime только
в памяти Vite. Исходники core/setup/plugins/adapters на диске не меняются.
Привязка к исходнику проверена якорем; применённый режим проверяется в тестах.

| Режим       | Изменение                                                                     |
| ----------- | ----------------------------------------------------------------------------- |
| baseline    | Исходный runtime; добавлены только наблюдения                                 |
| early       | `attachAll` сразу после сборки вместо ожидания эффекта                        |
| engine      | То же плюс собственный или родительский engine как ключ существующего TDrafts |
| engine-part | То же, но ключ отдельный для каждой пары engine / native mountId              |

Эффект продолжает принимать черновик и очищать сборку; повторный attach того же
контекста в эксперименте исключён, потому что исходный attach не идемпотентен.
Нативный ключ лифта берётся из родительского слоя по его описанию. Наблюдатель
получает и родительский, и созданный владельцем engine. В варианте engine-part
WeakMap хранит отдельную карту мест монтирования для каждого engine. Это
проверяемая гипотеза идентичности, не утверждённый production-механизм.

## Проверки

[SSR-опыты](./experiment.spec.tsx): активная вторая вкладка из разметки, контроль
через items, ListBox selected, поздний собственный id панели, Suspense fallback
без повторного выполнения Item, разрешившийся поток и настоящий abort потока.
Сохраняются исходный HTML и текущий состав engine.

[Клиентские опыты](./client.spec.tsx): настоящий hydrateRoot, сохранение узлов,
переключение кликом, StrictMode replay и unmount в jsdom. Записываются все
console.warn/error и recoverable errors. Диагностика не фильтруется и остаётся
в отчётах; она считается результатом опыта, а не скрытым успешным исправлением.
Нет проверки раскладки и физической клавиатуры в браузере.

Память: WeakRef на сборки, контексты, модели, bundles и engine; 20 завершённых
синхронных запросов и отдельно серии из 10 и 50 настоящих streaming abort. После освобождения
сильных ссылок — восемь отдельных turns с принудительным GC. Число наблюдений
включает повторные ссылки на один объект. Отдельный опыт намеренно сохраняет
родительский engine и проверяет состав после GC. Это проверка удержания внутри
живого владельца, а не доказательство утечки всего серверного запроса.

Зелёные тесты означают, что опыт выполнен и отчёт записан. Они **не означают**,
что каждый кандидат выдаёт правильный HTML. Неуспехи кандидатов сохраняются
данными, чтобы стенд оставался пригоден для следующего подхода.

## Результат текущего опыта

Полные HTML и наблюдения: [results/](./results/), сводка с версиями и исходным
commit: [summary.json](./results/summary.json).

- Ранний attach возвращает активную панель и правильный selected в ListBox.
- Ранее выданная первая кнопка Tabs сохраняет `tabindex=0`: при активной второй
  кнопке сервер выдаёт две остановки. Регистрация следующей вкладки уже не
  переписывает ранее сериализованный HTML.
- Поздний custom panel id также не исправляет уже выданный aria-controls таба.
- Прямое добавление общего engine в существующий TDrafts разрушает соседние
  непринятые сборки, включая владельца. Состав к концу рендера оказывается пуст.
- Ключ engine/mountId сохраняет соседей, но в принятом fallback остаётся ghost
  из приостановленной ветки. После разрешения потока в engine остаётся исчезнувший
  fallback. Повтор отсутствующего Item не возникает сам по себе.
- После 20 завершённых запросов наблюдаемые слабые ссылки очищаются во всех
  режимах. Это поддерживает гипотезу владельца об GC изолированного дерева.
- После streaming abort остаются наблюдаемые живые ссылки: baseline 7, early 13,
  engine 10, engine-part 21. В сериях 10 и 50 запросов числа одинаковы; роста
  в этой проверке не наблюдалось. Это число наблюдений, не уникальных объектов.
  Причина удержания последнего набора не установлена; отсутствие утечки при
  отмене не объявляется доказанным. Типы оставшихся объектов записаны в JSON.
- Удерживаемый engine сохраняет ghost при раннем attach и engine-part: GC не
  удаляет элемент из живой коллекции.
- Простой клиентский сценарий после эффектов и StrictMode работает в jsdom;
  это не устраняет неправильный исходный SSR HTML.

Граница результата: этот опыт не утверждает невозможность ранней регистрации.
Он показывает, какие именно гарантии пока не даёт прямой перенос attach и
расширение набора ключей TDrafts. Другие адаптеры, полная browser/Next-матрица,
нагрузочные замеры и production-выпуск здесь не проверяются.
