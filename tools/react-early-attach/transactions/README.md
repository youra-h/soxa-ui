# Неподтверждённая регистрация: commit, rollback, позднее восстановление

Проверка схемы владельца от 17.11.2026. Обычная модель сразу используется при
первой подготовке коллекции, рядом хранится запись её неподтверждённой сборки.
Attach подтверждает регистрацию; очистка pending-записи вызывает destroy всей
сборки. После rollback поздний render/attach восстанавливает сборку.

Это отдельный tools-прототип на настоящих исходниках Soxa/React. Он не использует
отменённую идею изолированного SSR, специальный Suspense, JSX-обёртку приложения,
новые props или перемещение данных между двумя storage. Production-файлы и
setup/protected на диске не меняются.

## Запуск

Из корня рабочей папки:

```sh
node node_modules/vitest/vitest.mjs run --config tools/react-early-attach/transactions/vitest.config.ts
node --import tsx tools/react-early-attach/transactions/browser.mjs
```

Первый запуск — реальные React SSR/jsdom lifecycle и GC-наблюдение. Второй —
настоящий Chromium, три цикла позднего Suspense, rollback перед attach и клики.
Сервер Vite и браузер закрываются запускателем. CSS темы не требуется.

## Реализация

[journal.ts](./journal.ts) хранит только pending-записи, числовой enum состояния,
ссылки на Item/контекст/engine и native initialize/destroy callbacks. Commit и
rollback удаляют запись из журнала. Один таймер обслуживает журнал, а не каждый
Item отдельно; когда записей нет, таймер снимается. WeakRef-массивы и счётчики
существуют только для наблюдений на стенде и очищаются между тестами.

[Конфиг](./vitest.config.ts) инструментирует в памяти три существующих узла:

- collection item extension выделяет из обычного attach регистрацию/meta в
  native `enter`, вызывает её при первоначальной подготовке и сохраняет прежний
  disposer. На attach выполняется commit того же Item, без повторной регистрации;
- collection owner extension отмечает attach/destroy владельца. До первого attach
  выполняется предварительная инициализация; при наличии живого владельца новый
  Item ждёт штатного attach. Пустота storage не используется как признак фазы;
- React runtime связывает pending-запись с `TBuilt.destroy`, делает destroy
  идемпотентным, отпускает ссылку TDrafts, восстанавливает destroyed-сборку перед
  повторным render и в уже существующем пути повторной установки эффекта.

На rollback вызывается destroy основной и facade-сборки. Штатный disposer снимает
регистрацию bundle и проводку, удаляет только модель, которой владеет регистрация.
Модель, уже принадлежавшая data engine, остаётся. Идентичность попытки — её context
и token, а не value: равные значения соседей не схлопываются.

Здесь операции commit/rollback пока реализованы журналом вокруг штатных команд
коллекции. Общие классы driver-команд в core не добавлялись: сначала проверяется
сама схема на native lifecycle, затем можно проектировать её место в общем слое.

## Почему важно переключение после attach владельца

Первый прямой вариант готовил все поздние Item во время render, включая уже живой
engine. React получил `Cannot update a component (Tabs) while rendering a different
component (TabsItem)` и повторял сборки. Этот вариант остановлен и исправлен.

Рабочий кандидат после attach владельца возвращается к обычному моменту
регистрации дочерних Item. Их непринятые сборки всё ещё учитываются и могут быть
уничтожены таймером. Поэтому поздний retry не изменяет живой engine во время render.
Это реализация предложенного переключения из предварительного режима в обычный,
по явной фазе владельца, а не по наличию первой записи storage.

## Проверки

- Обычный mount: prepare=2, commit=2, rollback=0; storage содержит те же модели.
- SomeComponent внутри обычного Suspense: до очистки A/B, после rollback только A,
  после разрешения ожидания снова A/B. Новая B имеет другую identity, pending=0.
- Удалённая ветка без retry: неподтверждённая регистрация освобождена, сосед A тот же.
- Внешний engine с data-моделью: истечение speculative mount не удаляет эту модель.
- StrictMode: после replay ровно A/B, без дублей и pending-записей.
- Rollback непосредственно из DOM-ref, до passive attach: сборки восстанавливаются
  штатным повторным эффектом, attach завершает commit.
- Серверные регистрации очищены до гидратации: свежая клиентская сборка сохраняет
  серверные DOM-узлы, без recoverable ошибок.
- Равные value у соседей: rollback удаляет только неподтверждённую регистрацию.
- SSR при намеренно удерживаемом внешнем engine: после таймера storage и журнал
  пусты. Слабые ссылки наблюдают модели, обе части контекстов и bundles.
- Streaming ждёт дольше TTL и затем создаёт новый Item: renderer завершается без
  ошибок, новые pending-записи также очищаются.
- 120 независимых Item: все регистрации откатываются, коллизий по engine нет.

В тестах TTL 30 мс, ресурс разрешается через 80 мс; в Chromium TTL 60 мс.
Пять минут реально не ожидаются: проверяется продолжение после истечения срока.
Событие загрузки body и знание границ Suspense не используются.

Сырые результаты: [client.json](./results/client.json),
[server.json](./results/server.json), [browser.json](./results/browser.json).
Console.warn/error не фильтруются; клиентские тесты требуют их отсутствия.

## Границы результата

Это положительная проверка схемы очистки/подтверждения/восстановления в выбранных
сценариях. Короткий WeakRef-прогон не является доказательством отсутствия любых
утечек. Отдельный долгоживущий pending Fiber React может законно удерживать свои
объекты; здесь проверяется освобождение связей со стороны коллекции/журнала.

Ранний SSR по-прежнему может сериализовать две Tab-остановки, позднюю ARIA-связь
или панель за пределами приостановленной границы. Rollback не переписывает уже
выданный HTML. Полная транзакционность активности/meta/событий, все внешние
потребители engine, группы/вложенность, другие адаптеры, Next/RSC и полный
install/browser/remote suite ещё не проверены. Бесконечно долгий SSR не объявлен
производственно поддержанным по одному короткому сценарию.

Следующий этап — короткий контракт общей реализации с владельцем: что входит в
pending-регистрацию, кто владеет записью/моделью, когда и что подтверждает commit,
как восстанавливается поздняя сборка и какие события разрешены до подтверждения.
