# Изолированное исполнение SSR: проверка времени жизни

Гипотеза владельца от 16.11.2026: сервер исполняет компонент в собственной
области, сериализует HTML, затем освобождает объекты; клиент создаёт свои.
Обычный consumer-контракт `Tabs.Item active` сохраняется.

Это tools-only опыт на настоящих React/Soxa исходниках, а не production
расширение и не перенос initial API из PR #882. На момент проверки PR #802
в этом репозитории относится к каталогу темы, поэтому механизм оттуда не
приписывается данному опыту. Точная историческая ссылка требует уточнения.

## Запуск

Из корня этой рабочей папки:

```sh
node node_modules/vitest/vitest.mjs run --config tools/react-early-attach/isolation/vitest.config.ts
```

Отдельный конфиг не применяет прежние варианты раннего attach и не меняет
продуктовые файлы. Vite инструментирует React runtime в памяти; setup/protected,
core и публичное API на диске не изменяются. Шесть тестов сохраняют результаты
SSR и гидратации в [results/](./results/).

## Модель опыта

[TIsolatedExecution](./scope.mjs) принадлежит host-коду тестового renderer.
AsyncLocalStorage различает запросы и продолжения потокового SSR. Каждый созданный
контекст регистрируется сразу после create, включая частично собранные контексты,
если последующая сборка бросит исключение. Внутри области включён ранний attach.
После синхронной сериализации либо завершения/ошибки/abort потока host вызывает
dispose: detach всех контекстов, destroy в обратном порядке, очистка сильных ссылок.

Проверяются только собственные модели из разметки. Явные внешние ctrl/engine
отклоняются до создания контекста; их клонирование, отображение и очистка не решены.
Это ограничение инструмента, не предлагаемый новый запрет для пользователей Soxa.
Включение неявного клиентского data renderer с ctrl тоже требует отдельной проработки.

На клиенте отдельно проверяются прежняя логика attach и ранняя начальная сборка.
Повторный attach в эффекте для уже подготовленной сборки исключён. Клиентская
ранняя сборка — только положительный синхронный контроль гидратации, её полная
безопасность при Suspense этим опытом не утверждается.

Глобальный callback-мост существует только в test-process для инструментирования.
AsyncLocalStorage и этот мост не предлагаются как portable setup/content API.
Приложение теста не получает специальной JSX-обёртки или новых props. Однако сам
SSR renderer вызывается нашим host-кодом: автоматическая доставка этой границы
из реального Next/Nuxt и других host в библиотечный компонент здесь не реализована.

## Наблюдения

- Синхронная активная панель выводится; после dispose собственные контексты
  уничтожены. В последнем прогоне все 31 слабое наблюдение этого запроса очищены.
  Две Tab-остановки уже сериализованы и остаются в HTML.
- Два параллельных разрешившихся потока и настоящий abort не смешивают области;
  dispose освобождает контексты каждого запроса. В последнем прогоне из 40 слабых
  наблюдений на поток остаются LEFT=0, RIGHT=1, ABORT=0. Тип/причина оставшейся
  ссылки не установлены; число includes повторные наблюдения одного объекта.
  Измерение выполнено после восьми отдельных turns с GC. Полное отсутствие
  удержания памяти этим коротким опытом не доказано.
- Ошибка приложения запускает тот же dispose. Контроль с внешним ctrl отклоняется
  и сохраняет его ARIA-снимок; поддержка внешнего engine этим не доказана.
- В пользовательском SomeComponent выполняется Item, затем Wait приостанавливает
  ветку. HTML содержит fallback и панель отсутствующей кнопки. Полная очистка после
  рендера убирает серверное состояние, но уже полученный неправильный HTML не меняет.
- После разрешения streaming Suspense до dispose коллекция содержит исчезнувший
  fallback. Изоляция запроса не сообщает, какие ветки внутри него React принял.
- Свежая клиентская сборка с прежним отложенным attach не совпадает с изолированным
  SSR: наблюдается recoverable hydration error и замена узлов.
- Свежая клиентская сборка с такой же ранней инициализацией сохраняет узлы без
  console/recoverable diagnostics в проверенном синхронном примере.

## Архитектурная граница

Идея разделяет серверное и клиентское время жизни и позволяет исследовать
детерминированное освобождение серверных ресурсов. Она сама по себе не определяет
принятый состав Suspense и не подготавливает сведения о поздних соседях до раннего
HTML. Для корректного результата нужны оба свойства, не только последующий destroy.

Кандидат ответственности setup/content — владелец собственных ресурсов,
инициализация и dispose. Native исполнение дочернего дерева, завершение/abort SSR
и гидратация принадлежат адаптеру/host. Расширение setup не получает эти сигналы
автоматически и не может просто вызвать произвольный React-потомок как функцию.
Сначала требуется доказать нативную доставку границы исполнения при прежнем
consumer API; только затем выбирать production-размещение.

Другие адаптеры, browser/install-smoke, Next/RSC, внешние модели, произвольные
плагины и динамическая клиентская коллекция здесь не проверяются. Из результата
не следует ни готовность решения, ни невозможность более полной изоляции.
