# Подготовка SSR и очистка непринятых сборок

Проверено 18 ноября 2026 года, Windows, Node 24.20.0, React 19.3.1.

Подготовка данных PR #900 объединена с транзакциями из PR #892. Ранее падавшая
проверка памяти теперь проходит на собранных продуктовых пакетах, без подмены
React runtime. Экспериментальный инструмент подмены удалён, регрессии перенесены
в штатные тесты адаптера React.

## Реализация

- Driver лениво создаёт реестр неподтверждённых попыток с commit, rollback,
  cancel, владельцем и общим таймером ближайшего deadline.
- Core-расширение `TPreparationExtension` открывает этот механизм через
  обычный контракт расширения, без доступа setup и UI к driver.
- `TCollectionPreparation.pending` связывает подготовленную коллекцию с
  уничтожением всей нативной сборки, включая её фасады. Исходные модели
  коллекции не удаляются. Обычная сборка без `initial` транзакцию не создаёт.
- React подтверждает receipt при принятии. Непринятая сборка через 1000 мс
  уничтожается и освобождает `TDrafts`. Поздний render или установка эффекта
  восстанавливает её из того же источника подготовки.
- В отличие от первоначального варианта #892, таймер держит WeakRef реестра.
  Завершённый запрос со своим движком может освободиться до timeout. Внешний
  живой движок сохраняет свой реестр и обеспечивает rollback по deadline.

Это сохраняет назначение обоих механизмов: начальные данные известны до HTML,
а непринятые временные ресурсы освобождаются. Автоматическое обнаружение Item
в произвольных обёртках не добавлялось; вход `initial` остаётся прежним.

## Порядок и объём проверок

Сначала повторены упавшая проверка внешнего engine и три критических случая
позднего Suspense. Только после их прохождения запущены затронутые тесты и
нагрузка. Полный прежний прогон 21479 тестов заново не повторялся.

Проверены завершение и отмена server stream, поздний Item после rollback,
клиентский retry, rollback между DOM insertion и passive acceptance,
гидратация прежних DOM-узлов после уничтожения серверной сборки, сохранение
точной идентичности моделей и отсутствие повторной начальной активации.

После интеграции прошли 11 тестов транзакций core, 45 тестов подготовки setup,
220 React-тестов SSR/initial/внешнего lifetime/удержания props, включая четыре
новых сценария rollback. Проверены типы core, setup и React вместе с тестами.
Целевые `collection-initial` наборы остальных адаптеров также прошли:
Vue — 14, Solid — 16, Svelte — 21, Web Components — 2, Angular SSR — 12.
Исходная полная приёмка сохранена в [README.md](./README.md).

## Память

[Проверка внешнего engine](./results/integrated-memory.json): для завершения
и отмены SSR по 12 запросов с 12 моделями. Каждый исход создаёт 444 bundles и
12 источников. После 1200 мс и GC остаётся **0 bundles и 0 источников**, при
этом исходные модели каждого внешнего engine сохранены по идентичности.
Раньше оставались 156 bundles и 12 источников.

[Матрица памяти](./results/integrated-memory-matrix.json): 16 отдельных процессов,
100/1000 Tabs, простые/вложенные метаданные, `initial`/обычный `items`,
завершение/отмена server stream. Всего 144 измеряемых запроса, дополнительно
прогрев. Все наблюдаемые запросные источники и движки собраны GC: **0 живых**.
Это наблюдение для выбранных сценариев, а не доказательство отсутствия любых
утечек в любом приложении.

Inspector-профили и RSS относятся к отдельным процессам, включают прогрев,
загрузку модулей и накладные расходы профайлера. Подробные величины по раундам
есть в JSON; их нельзя интерпретировать как точный размер временного SSR-графа.
Для 1000 Tabs в режиме `initial` post-GC heap составил 24,7–26,7 MiB,
прирост от прогретой базы — 0,84–0,89 MiB, процессный peak RSS — 331,5–344,6 MiB
в четырёх сценариях завершения/отмены с разной глубиной метаданных. Из этих
значений не вычисляется точная дополнительная стоимость транзакций в памяти.

## Производительность

Последовательный production `renderToString`, 4 прогрева и 15 измерений на
каждый вариант, чередующийся порядок, GC за пределами измеряемого участка.
Две сборки имеют одинаковые настройки и одинаковые текущие core/setup/plugins.
Контроль использует только React runtime до интеграции, из коммита `3d2a372e0`.
Таким образом измерена добавленная механика транзакций, а не все изменения
относительно #882. HTML проверен на равенство после нормализации generated ID,
единственную tab-остановку и взаимные ARIA-связи.

| Tabs | Метаданные | До, медиана мс | После, медиана мс | Разница |
| ---: | ---------- | -------------: | ----------------: | ------: |
|  100 | Простые    |          13,16 |             13,24 |   +0,6% |
| 1000 | Простые    |         116,16 |            117,39 |   +1,1% |
|  100 | Вложенные  |          17,82 |             17,74 |   −0,4% |
| 1000 | Вложенные  |         160,77 |            156,02 |   −3,0% |

Существенного ухудшения в этом прогоне не обнаружено; разнонаправленные
небольшие отличия не следует трактовать как доказанное ускорение. Вложенность
здесь относится к payload метаданных, а не к вложенным Tabs. HTTP, browser,
RSC и время гидратации не измерялись.
[Все выборки, p95 и хеши сборок](./results/integrated-performance.json).

## Повторение

После сборки пакетов, из корня рабочей папки:

```powershell
$env:NODE_ENV = 'production'
node --expose-gc tools/ssr-acceptance/external-memory.mjs
node --expose-gc tools/ssr-collection-prototype/initial-memory.mjs
node tools/ssr-acceptance/build-comparison.mjs
node --expose-gc tools/ssr-acceptance/performance.mjs
Remove-Item Env:NODE_ENV

npm.cmd run test --workspace=@soxa-ui/core -- collection-transactions
npm.cmd run test --workspace=@soxa-ui/setup -- assembly-preparation collection-initial
npm.cmd run test --workspace=@soxa-ui/react -- collection-initial
```

Сравнительная сборка использует исторический runtime только в tools-выходе;
продуктовые исходники на диске не меняются. Исходный объект Git `3d2a372e0`
должен быть доступен локально. Результаты локальных запусков и нового CI
следует различать; прежний WebKit CI не запустил тесты из-за отсутствия
`libicudata.so.74`.
