# SSR acceptance: PR #900

Проверено 18 ноября 2026 года на Windows, Node 24.20.0, production React.
Исходная ревизия: `14906545d0380f552ea48f4cc0aa1fbd10256d41`.

**Приёмка остановлена на утечке временных сборок при живом внешнем движке.**
Проверки производительности и сравнительный нагрузочный прогон не запускались:
сначала необходимо устранить обнаруженное удержание объектов в продуктовом коде.

## Воспроизводимая утечка

[external-memory.mjs](./external-memory.mjs) выполняет настоящие завершённые
и отменённые React server streams. На каждый исход создаются 12 внешних движков,
каждый с 12 исходными моделями. Движки намеренно остаются живыми. Наблюдение
использует WeakRef без шпионов, сохраняющих аргументы вызовов. После 1200 мс
выполняются четыре GC через отдельные обороты очереди. Проверяется также
сохранение точной идентичности внешних моделей.

| Сценарий                                | Bundles создано / осталось | Источников создано / осталось |
| --------------------------------------- | -------------------------: | ----------------------------: |
| Текущий PR, завершённый SSR             |              444 / **156** |                   12 / **12** |
| Текущий PR, отменённый Suspense SSR     |              444 / **156** |                   12 / **12** |
| Эксперимент с rollback, завершённый SSR |                444 / **0** |                    12 / **0** |
| Эксперимент с rollback, отменённый SSR  |                444 / **0** |                    12 / **0** |

[Текущий результат](./results/external-memory.json),
[результат эксперимента](./results/rollback-external-memory.json).

После отпускания внешних движков текущий вариант также освобождает наблюдаемые
объекты. Причина удержания — `TDrafts`: WeakMap имеет живой внешний engine ключом,
а значение содержит `TBuilt.destroy`, через которое доступны контексты и bundles.
Без нового рендера того же engine и без commit такая запись не освобождается.
Сам файл реестра не менялся между базой PR #882 и PR #900; это не доказательство
новой регрессии исключительно от рефакторинга #900.

Контроль старого теста: 1000 Tabs, 9 отменённых запросов с собственными движками —
9/9 движков и 9/9 источников собраны GC. Наблюдаемый post-GC heap вырос примерно
на 0,79 MiB, процессный peak RSS составил примерно 316 MiB. Это один отдельный
профилируемый сценарий, включающий накладные расходы Inspector и прогрева;
это **не** сравнение производительности и не измерение точной стоимости SSR.
[Сырые данные](./results/request-owned-memory.json). Он объясняет, почему
проверка только объектов, принадлежащих запросу, пропускала найденную утечку.

## Проверка commit / rollback из прежних PR

Просмотрены актуальные ветки PR #881, #882, #886, #892 и #900. Старые тесты
не копировались вслепую: #881 проверяет отвергнутый двухпроходный сборщик,
#886 — раннюю регистрацию, #892 — декларативные модели с pending-транзакциями.
В #900 модели объявлены заранее. При rollback внешние модели должны сохраниться;
старое ожидание «удалить все speculative Item из пустого engine» здесь неприменимо.

[rollback-probe.mjs](./rollback-probe.mjs) берёт три файла транзакций **без изменений**
из PR #892, коммит `8ed2df2ac21544d20e69df7055994057378c64a3`, и инструментирует
только сборку текущего адаптера React в памяти Vite:

- неподтверждённая сборка получает receipt с timeout 1000 мс;
- React acceptance делает commit;
- rollback уничтожает всю сборку и освобождает запись `TDrafts`;
- поздний render или повторная установка эффекта восстанавливают сборку.

Это **tools-only эксперимент**: продуктовые исходники, публичный API и механизм
рендеринга React не изменены. В эксперименте один общий реестр обслуживает
сборки; это не готовая интеграция реестра в Collection Engine. Раннее добавление
Item из старого PR не переносилось.

В эксперименте прошёл полный React-набор: 1916 штатных тестов плюс две новые
клиентские проверки. Отдельно прошли три проверки срока жизни:

1. Поздний retry обычного Suspense после rollback: исходные модели сохранены,
   HTML корректен, переключение вкладок работает.
2. Rollback после DOM insertion, до passive acceptance: сборка восстанавливается.
3. Нативный серверный stream продолжает работу после rollback, затем создаёт
   подготовленный Item: две вкладки, одна tab-остановка, выбранная панель и ARIA-связь.

Native server и client проверки находятся в разных тестовых модулях: совмещение
рендереров на одном экземпляре React Context вызывает предупреждение React.
Сторож console.warn/error не отключался.

Прохождение этих сценариев показывает применимость механизма очистки. Оно не
доказывает отсутствие всех утечек, готовность окончательной архитектуры или
стоимость механизма на нагрузке. До нагрузочных сравнений нужны продуктовая
интеграция и повторная приёмка получившейся реализации.

## Повторение

Из корня рабочей папки, после сборки пакетов:

```powershell
$env:NODE_ENV = 'production'
node --expose-gc tools/ssr-acceptance/external-memory.mjs
# На исходном коммите ожидается exit 1: это реально падающий acceptance gate.

node tools/ssr-acceptance/rollback-probe.mjs --build
$env:SSR_REACT_MODULE = './results/rollback-adapter/index.js'
node --expose-gc tools/ssr-acceptance/external-memory.mjs
Remove-Item Env:SSR_REACT_MODULE
Remove-Item Env:NODE_ENV

node node_modules/vitest/vitest.mjs run --config tools/ssr-acceptance/rollback.vitest.config.ts
```

Эксперимент извлекает исходники транзакций из локального Git object database.
Продуктовые сборки и экспериментальная сборка используют одни и те же собранные
core/setup/plugins: не появляются вторые копии реестров классов. JSON содержит
хеши продуктовых dist и отдельный хеш экспериментального адаптера.
